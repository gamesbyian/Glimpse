## Release boundary and classification

The November 8 conversational release audit used local blocker numbers **#1–#41**. These are **audit-item identifiers, not GitHub issue numbers**. Each appears under exactly one primary campaign below; an acceptance case may involve several campaigns. Use issue links with explicit `issue` or `PR` labels to avoid confusing the two.

- **Safety stop:** known possible loss/overwrite of photos or Room data, misleading wallpaper acknowledgment, release-signature incompatibility or untrusted privileged release operations. Keep the release gate until independent proof or elimination of the risky path. No waiver by downgrading test assertions.
- **First-sideload M1 acceptance:** primary import → persistent private copy → Reel/Grid preview → explicit Home apply → honest active-use rotation, plus applicable privacy, accessibility, device and upgrade qualification. A truthful, explicitly limited M1 can ship without all M2/M3/M4 concepts, **but no initial-release scope has been newly approved by this document**.
- **Conditional distribution gate:** e.g. owner-chosen app signing/release channel, public asset rights, Pages publication if enabled. Owner/configuration prerequisites remain visible; code cannot silently claim these finished.
- **Later product scope:** M2 controls and M3/M4 research. Do not describe absent advanced features as launch defects if the owner selects a narrower M1. Do not count an unimplemented workflow as complete.

## Cross-campaign dependencies and shared acceptance

1. **Source/owner configuration:** R0 defines the release boundary. R2 can prepare verification before the owner creates the protected key, but **no protected-signing acceptance** exists until the same public cert is observed on two independently built APKs. A temporary signer is useful testing evidence only.
2. **Single data-preservation path:** R1 implements no-clobber publication, receipts, Room audit/recovery and guarded removal in separate small PRs. R2 runs installed-data upgrades against these invariants; R6 exercises their visible import/recovery UX. An unsafe automatic cleanup cannot be hidden behind a passing upgrade test.
3. **Single wallpaper authority:** R3 owns OS mutation/uncertainty, scheduling admission and eligible/shuffle state. R6 drives it through real UI and Share/Picker routes; R4 validates honest rendered states and accessible recovery. Widgets and Quick Settings may invoke the gateway but never create competing apply engines.
4. **One owner-device matrix:** R4/R5/R6 share a planned physical Pixel pass: 0/1/3/22/60 and representative large collections, narrow/200% text, TalkBack/Switch/keyboard, gestures and scroll interruption, offline provider states, OS delay and real visual reference review. Record **independent observations** for each acceptance class; shared test execution must not collapse different assertions into a single vague green badge.
5. **One candidate provenance bundle:** R2 collects exact main SHA, tested APK SHA-256, public cert fingerprint, version/app ID, OS/device variants, failed attempts, screenshots/hierarchy and owner decisions. The final release table links R1–R6 evidence. A green check on an earlier commit, a skipped check or a draft PR is not current-candidate acceptance.

## Preventing the duplication from coming back

- Each conversational blocker gets **one campaign owner** and one issue/queue evidence path; related acceptance is cross-linked rather than copied into new tickets. When multiple problems share a root cause, fix and test it once at its source, then add distinct regression assertions for each symptom.
- Do not create a 41-ticket release backlog, another database, another recovery writer, another wallpaper executor, or a mega-PR spanning unrelated app layers. Campaigns coordinate **small, independently reviewable** PRs with explicit file ownership.
- Keep historical checkpoints as historical records. Current work, open gates and near-term dependencies belong here and in the top of [implementation queue](implementation-queue.md); agent instructions should link to the current map rather than reciting possibly stale status.
- **CI P2 efficiency** [#161](https://github.com/gamesbyian/Glimpse/issues/161) and [#191](https://github.com/gamesbyian/Glimpse/issues/191) remain useful infrastructure work, **not separate app-release blockers** unless they compromise required evidence, provenance or viable testing. Never optimize away the exact real Android checks.
- A test-only personal APK and a public/data-preserving release have different acceptance bars. Neither silently overrides the owner's product/visual choices; neither authorizes deletion of user photographs.
